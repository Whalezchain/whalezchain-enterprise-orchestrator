# WhalezChain / CometBFT ABCI++ implementation contract

Status: implemented and exercised on an **isolated, same-device four-validator internal devnet**. **NOT** production mainnet certification.

## Canonical architecture

The existing WhalezChain Python `MainnetStateTransition`, `MainnetChainStore`, genesis/asset registry, and replay logic remain the canonical economic state machine. No replacement blockchain, parallel ledger, or independent financial authority is introduced.

- CometBFT: block proposal, consensus, validator voting, block ordering, peer networking, and signed headers.
- Go `consensus/cometbft_abci`: native CometBFT ABCI++ socket API; calls only a private UNIX-socket Python endpoint. The Go transport has no ledger mutation or signer authority.
- Python `mainnet/cometbft_abci_server.py`: private UNIX socket with restrictive file permissions; delegates to `WhalezCometApplication`.
- `mainnet/cometbft_state_machine.py`: deterministic transaction admission, process/proposal validation, application-hash construction, staged `FinalizeBlock`, canonical `Commit`, persisted replay and crash-restart checks.
- `consensus/cometbft_abci/cmd/verify_commit`: separate verifier using CometBFT's *official* signature verification against pinned genesis voting power and the WhalezChain application hash committed in a signed header.

## Height and state mapping

For a fresh, synthetic laboratory genesis: CometBFT height 1 maps to WhalezChain block height 0. The WhalezChain application hash commits both the balance state root and economic state root, plus the canonical WhalezChain block hash and CometBFT height. The ABCI transport does not mint, settle or custody assets.

The demo adapter explicitly admits only signed native *transfer* transactions. No minting, issuance, settlement, payroll, bonded settlement, external wallet, or real allocation is allowed through this adapter. Any unsupported transaction is rejected before state mutation.

`FinalizeBlock` stages deterministic data; `Commit` is the only canonical mutation point. Production `MainnetChainStore.require_verified_network_finality` is still fail-closed. The devnet-specific Comet decision marker is not a substitute for production independent finality authorization.

## Runtime and safety separation

This code requires a devnet-prefixed Comet chain ID, a synthetic `authority_config.mode=test` genesis, and mainnet financial execution disabled. The Go ABCI server binds only to IPv4 localhost. The Python backend is a private UNIX socket in a 0700 directory, socket mode 0600. No production validators or production signing keys are generated by the devnet scripts.

The scripts generate four temporary CometBFT validators, four separate WhalezChain state stores, and isolated synthetic test balances. Generated node keys, genesis files, WAL, logs and receipts MUST NOT be added to Git or reused as production chain state.

## Verified engineering acceptance

Local integration demonstrated real four-validator CometBFT block production, signed synthetic PTN transfer, identical canonical block hashes at equal heights, deterministic replay, independent cryptographic verification of four-validator and three-validator commits, rejection of a forged expected application hash, continued 3-of-4 block production after a validator shutdown, and rejoin/catch-up from the stopped node's own data. An additional same-device negative quorum experiment stopped two validators, observed no finalized-height advancement at 2-of-4, then restarted the original validators and verified resumed consensus with matching canonical blocks. This is not a separate-host network-partition test.

These tests do **not** establish four independently operated hosts, production key custody, independent networking, disaster recovery, adversarial network partition safety, production governance ratification or external financial settlement certification.

## Offline signed-finality evidence and consistent reader boundary

The independent Go verifier supports two distinct modes: `--rpc --proof-out` verifies a live canonical signed header, checks the trusted genesis validator powers and WhalezChain application hash, and writes a bounded 0600 signed-header proof without overwriting existing evidence. `--proof-in` requires no RPC connection and re-runs CometBFT's actual cryptographic signature and quorum checks against **separately supplied** trusted genesis and expected WhalezChain state hash. A raw `verified: true` response is never itself an authorization.

The important height contract is explicit: CometBFT signed header height H proves the **preceding application hash**, which commits WhalezChain block height H-2 in the current genesis mapping; it does not itself certify the current H block. A separate, private, 0600 `offline-proof-receipt.json` records the verified height, roots, signed votes, trusted genesis digest and proof digest, with fail-closed wrong-height, wrong-state and forged-header controls. The receipt is created with exclusive no-overwrite semantics, fsynced to disk. It is not a Founder financial authorization, production finality release or an external certification.

The canonical `MainnetChainStore.verified_snapshot()` provides a shared-lock, replay-verified, detached read for wallets, chain inspection and audit consumers. It cannot observe half-committed head/index metadata while `append_finalized_block` holds the exclusive writer lock. Consumers should use it rather than combining independently timed `replay_state()` and `verify_chain()` calls.

The full four-node acceptance script now exports the signed header proof before shutdown; a **separate** offline verification step runs after all CometBFT validators have stopped. CI runs the same boundary and rejects any missing, forged or replayed proof. The generated proof, runtime keys and private audit receipts never enter Git.

## Reproducibility and release hold

Source dependency: `github.com/cometbft/cometbft v0.40.0` with `go.mod` and `go.sum` pinned in the existing orchestrator repository. The unmodified upstream source embeds a fallback `TMCoreSemVer` constant `0.39.0`, so the locally compiled executable prints `0.39.0` even when built from the v0.40.0 module path. Production binary provenance must be independently reconciled (verified tag/commit, hashes, SBOM and supported release status).

All run receipts and temporary keys remain in the private review workspace. Do not publish live runtime topology, private identity, signer configuration, or sensitive receipts into public-facing services.

Before enabling a production release: use independently operated validator hosts; secure validator identity and key management; test full process crash, network partitions, persistent restore and independent replay; verify exact-head CI/security; ratify canonical genesis and validator admission; and satisfy the separate immutable approval/nonce consumption and custody gates. Production cutover and all external financial operations require specific authorization and evidence.
